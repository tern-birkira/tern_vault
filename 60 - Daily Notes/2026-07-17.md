## System Requirement for per placeholder changes.

The architecture requires a strict context-aware mapping layer that bridges runtime configuration keys to precise compile-time properties (`Q_PROPERTY`), preventing type-based cross-contamination across different model types. While multiple schemas share identical primitive types (like an `int` for font size), the underlying XSD grammar dictates that a specific configuration key must only target its bound domain model, regardless of how many instances of that model exist. Therefore, your editor needs to validate runtime data modifications against the instance's specific class type and its registered metadata, ensuring that key updates selectively alter only the instances of the matching domain type while completely ignoring other objects with identical data signatures. [1]

## Conceptual Example

Imagine your tree contains four separate object instances in memory, three of which happen to have a property named `font_size` (type `int`):

- 📂 Root Node
    
    - 📄 `Instance_1` of `ModelA` (has `int font_size`)
    - 📄 `Instance_2` of `ModelA` (has `int font_size`)
    - 📄 `Instance_3` of `ModelB` (has `int font_size`)
    - 📄 `Instance_4` of `ModelC` (has `QString name`)
    

## The Runtime Input:

Your editor receives the following instruction from a file or UI grouping:  
`my_font_size : 24`

## Expected Enforcement Behavior:

- ✅ Allowed: `Instance_1` (`ModelA`) updates its `font_size` to `24`.
- ✅ Allowed: `Instance_2` (`ModelA`) updates its `font_size` to `24`.
- ❌ Blocked: `Instance_3` (`ModelB`) completely ignores the command because the key `my_font_size` is strictly forbidden to touch `ModelB`, even though it features an identical `int` property.
- ❌ Blocked: `Instance_4` (`ModelC`) ignores it due to a complete type/key mismatch. [2]
