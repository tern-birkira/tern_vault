OK we have taken a turn about how the architecture of the import/export. We have decided to have a large portion of the program hardcoded, the models, with its roles.

We have decided to shift from the generictree format, this would mean that we have different method of exporting and saving per editor,

we would have a translation layer; XmlDocument* toXml ( tracklabel ) and trackLabel fromXml ( XmlDocument ).

  

XmlDocument knows about its types from the schema, and the domain layer (models) know about their types because they are hardcoded.

  

This would also mean that changes made in the schema NEED to have a change in the code, new hardcoded types.

the mapping needs to 1:1.

  

This would eliminate the need for the GenericTree, because the model itself coverns the structure (and its submodels), witch the translation layer goes to and from. So the translation layer uses tern::xml internals straight up. When saving from one to another, the translation layer, the reciever requests the corresponding type from the sender.

  

The benefit of this are; easier and type safer implementation (when versions match). Easier implementation of dynamic and beautiful UI, (because models know more about there types).

drawback; harder maintanence between schema and source code.

  

The main thing that i am thinking is: We really want to keep the hardcoded roles, but, i would really like to have some kind of generic tree structure which knows how to save into xml, meaning i do not need to create different translation layers between different editors (that is different configs, that have different tree xml structure).

I was thinking this; as of now we have structured the project such that the models govern the structure. What if we define the tree with the models that are in place, call it model tree? when saving, the tree wrapper or whatever you want to call it, knows how to save, since it was defined by the structure of the models.

This would create a generic to and from xml translation functions, which only need to take in the model tree, because it knows how to save itself.
